# Unpackaged upgrade from published 1.6.0 on VMware

Test date: 2026-11-17, Europe/Moscow. A dedicated VMware NAT guest ran Ubuntu
24.04.5 LTS amd64, HAProxy `2.8.30-0ubuntu0.24.04.2`, PostgreSQL 16 and systemd
`255.4-1ubuntu8.18`. It was provisioned from the same authenticated Ubuntu image
as the [previous pristine test](1.6.1-pristine-vmware-b5fa4a4.md), with a fresh
disk, fixture SSH key and a host key pinned from the local serial console.
There was no easy-waf state before installation.

## Starting installation

The [authenticated published 1.6.0 tarball](1.6.1-release160-migrations.md)
matched SHA-256 `b9d3e11362003c37b9d7c346f3be297ec4c15471fef9b0fd1a673a2cac7a5066`.
The tagged install script used its extracted `dist` and default dependencies,
including local PostgreSQL, CrowdSec, HAProxy and Fail2Ban. The root installer
returned 0. A fixture `EASY_WAF_VERSION=1.6.0` value supplied the old API's
display version. The instance had no easy-waf package in dpkg, four installed
binaries matched the tarball, three daemon executables matched their installed
files, and the migration ledger contained 19 records ending at 019.

A dedicated operator enrolled through the management API. A loopback HTTP
backend served a fixed marker through a test HTTPS publication under `.invalid`.
The first publication attempt returned HTTP 422 because the fixture's umask
removed group traversal from its PEM directory. Correcting that owned directory
mode allowed the write and Apply. An HTTPS client verified the public fixture
certificate and marker. The old HAProxy stats socket was absent even though the
generated configuration declared it. The HTTPS baseline passed independently
of that observation.

## Actual wrapper and follow-up checks

The exact source tree at `7a1499b15c3dd637bf99bead9c71edff6384887f` supplied the
wrapper and installer. Its explicit input was the [inspected bccbf26 amd64
tarball](1.6.1-upgrade-160-bccbf26.md), SHA-256
`f6160fe22312c5e5d0cdcb83f234e93a23d0d843b19de3bd00aabc2231202308`.
The commits differ in shell scripts, documentation and ShellCheck registration.
The Go binaries reused here came from bccbf26. The 1.6.1 candidate was unsigned.

The actual `scripts/upgrade.sh` completed with exit 0 and systemd accepted the
active-only API and ACME restart requests. The broker, API and ACME invocation
IDs changed, and all three running executables matched the candidate binaries.
The candidate API reported 1.6.1, the ledger advanced to 28 records ending at
028, and easy-waf remained absent from dpkg. Publication and certificate IDs,
checked row fields, PEM bundle hash, served leaf and marker response matched
the baseline. No manual service restart was required after the upgrade.

The post-upgrade harness initially failed at its whole-file `easy-waf.env`
hash assertion. The default installer ran CrowdSec bootstrap, which re-registers
bouncers and writes `CROWDSEC_LAPI_*`. There is no byte-for-byte env preservation
claim. The independent follow-up confirmed management login, the authenticated
CrowdSec decisions read, a working HAProxy stats socket with a backend UP, no
pending edge changes, and an explicit API Apply followed by the same trusted
HTTPS response and statistics. A separate Windows client verified the exact
leaf and marker through the VM's NAT address. Authenticated appliance smoke
passed 19 checks, failed 0 and skipped 2 (legacy admin token and optional MMDB).

The backup timer was active and no systemd units remained failed after clearing
the owned test units. The dedicated guest was powered off with private logs and
credentials retained on its disk. The restore clone and PVE appliance were
outside the test scope. This covers the unpackaged amd64 path with API Apply.
Manual browser Apply and final signed-release acceptance remain separate checks.
