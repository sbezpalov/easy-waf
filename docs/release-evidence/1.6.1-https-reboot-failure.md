## Actual reboot with published HTTPS

A temporary loopback backend was installed as an explicitly named test-only
systemd unit, running as the existing unprivileged operator account. It used
`NoNewPrivileges`, a private temporary directory and read-only filesystem/home
protections. Its HTTP route returned only a unique nonsecret marker.

The authenticated, password-confirmed management API published it through
HAProxy using the already issued production certificate. No new certificate was
requested. Before reboot, a TLS client on the VM used public-name SNI and the
unmodified OS trust store, and received the exact backend marker with HTTP 200.
The served certificate fingerprint and expiry matched the database.

A real reboot changed the kernel boot ID. Afterwards:

- All ten checked appliance services and the test backend started automatically.
- Trusted HTTPS returned the exact marker with HTTP 200.
- The same certificate survived reboot; its served leaf fingerprint and expiry
  still matched the database.
- Authenticated appliance smoke returned exit 0. Final recorded smoke was
  18 passed, 0 failed, 2 skipped (legacy admin token and optional MMDB upload).
- The owned application was deleted through the API; only the named test unit was
  disabled, stopped and removed, followed by daemon reload. Its absence was verified.

This closes the published-HTTPS gap in the previous reboot observation. Late
PostgreSQL recovery was separately demonstrated on the same binary candidate in
[the initial PVE record](1.6.1-336b5e0.md). Post-reboot HTTPS was probed from the VM;
the independent mobile WAN request was a separate earlier observation, not a
second mobile request after this reboot.

## Isolated HTTP-01 failure and recovery controls

A unique unused child of the operator-provided test hostname was confirmed
NXDOMAIN with the native DNS resolver. One owned certificate row was created in
**staging**, explicitly using HTTP-01. The global production setting and existing
production certificate were preserved. No DNS records, listening ports or network
rules were changed, and no production issuance was requested.

The real worker/CA attempt produced the expected DNS validation failure:

| Observation | Result |
|-------------|--------|
| Stored ACME status and error | `failed`, NXDOMAIN present in the recorded error |
| Consecutive attempts | 1 |
| Retry delay from recorded update time | 600 seconds; next attempt still in the future |
| Certificate summary API | Failed status, last error, next-attempt time and attention present |
| Worker journal | Actual issuance-failure entry observed |
| Worker restart | Failure/backoff persisted; no second attempt was claimed |
| Startup attention sweep | Expected certificate warning appeared after worker restart |
| Production certificate | Remained ready with production mode unchanged |

The ordinary daily attention interval was not accelerated or waited out. The
warning observation above is specifically the real startup sweep after restart;
raw errors and selected journal lines remain root-private on the VM. Dashboard
**API data** was checked; rendered management UI and optional webhook/Telegram
notification delivery were not exercised.

The owned failed staging row was deleted before its scheduled retry, avoiding
unnecessary repeated CA requests. This verifies a real DNS failure during HTTP-01;
it does not claim that an established hostname's TCP port was deliberately blocked,
or that a failed renewal with an older valid certificate was tested here.
