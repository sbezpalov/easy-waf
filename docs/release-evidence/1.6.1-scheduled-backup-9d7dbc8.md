# Packaged timer-driven backup on VMware

Test date: 2026-11-17, Europe/Moscow. The dedicated VMware guest ran Ubuntu
24.04.5 LTS amd64 with the [pristine 9d7dbc8 installation](1.6.1-pristine-vmware-9d7dbc8.md).
The installed timer, service, backup script and its two shell helpers matched
the verified amd64 DEB. The current `main` tree at `1cedf5a` had identical
backup inputs. The DEB SHA-256 was
`dcabff25832c1873960bbecb5752f40e3489ef7d6ed04f591360541203f808f9`.

## Trigger and archive

The fixture changed only the timer's next activation and the service's output
settings through runtime drop-ins. The timer used a five-second delay with zero
jitter and persistence disabled for the fixture. An additional service
environment file directed output to a new private directory on the guest. The
packaged service command was unchanged. The test started the timer; the actual
backup service ran without a manual start request. Its start timestamp and the
timer's last trigger changed. The service reported `Result=success` and
`ExecMainStatus=0`.

The service produced exactly one root-owned `0600` archive. The gzip checksum
and tar listing passed. The archive contained the manifest, appliance env,
HAProxy state and a custom-format PostgreSQL dump. `pg_restore --list` found
the application data and migration ledger. `pg_restore --file=/dev/null` read
the dump without modifying a database. A transient unpacked dump was removed;
the archive and private logs stayed on the VM. A subsequent trial restored
that same archive as described below.

## Recovery and cleanup

API and ACME both returned active with new invocation IDs. The owned HAProxy
publication returned its exact marker on all 21 samples while the timer and
backup ran, and again after completion. After the test overrides were removed,
the original persistent timer stamp matched its recorded state. The daily timer
was again active and enabled with a real-time next activation. No unit remained
failed. An independent Windows client received the expected publication response.
Authenticated smoke from `1cedf5a` passed 20 checks, failed 0 and skipped 2
(legacy admin token and optional MMDB upload).

## Restore of the timer-created archive

A second run on the same guest confirmed that the installed restore command
matched the DEB. It paused the normal timer and made a fresh private checkpoint
of the pre-test state. The management API then put the fixture application in
maintenance mode. A new HTTP request returned 503.

The installed `easy-waf-restore` command used the exact archive retained from
the scheduled backup and returned 0 with a successful console Apply. The archive
checksum matched before and after restore. The original application ID, backend
and checked timestamps returned, and maintenance cleared. The same route
returned HTTP 200 and the expected body. The live env and management certificate
matched the archived files byte for byte. PostgreSQL retained schema 028,
HAProxy reported a backend UP, and saved and applied edge generations matched.

The test then restored its pre-test checkpoint and resumed the normal timer.
The original publication, selected configuration files and running services
passed verification. No systemd units were failed. An independent Windows
client verified the marker, and authenticated smoke again passed 20 checks
with 0 failures and 2 skips. Both archives stayed on the VM.

The dedicated guest was powered off. The PVE appliance and the separate VMware
restore clone were outside the test scope.
