# Rejected Apply and revision rollback — e02aebb

On 2026-11-24, a clean Ubuntu 24.04.5 amd64 VMware guest installed the
[verified e02aebb ISO](1.6.1-packages-e02aebb.md) without a network adapter.
Authenticated About reported 1.6.1 and
`e02aebbe36ea3ca52e3cb066e8a9f5f05883ab5a`. The test used a temporary
loopback publication and a local trust anchor.

With the baseline serving trusted HTTPS 200, the password-confirmed
management API saved an otherwise valid SPOE engine name that did not
exist in the installed SPOE file. Apply returned 422. The API journal
confirmed that the actual `haproxy -c` parser had rejected the staged
configuration. The managed config, certificate list and maps retained
their hashes and modes. The master, worker and revision list were unchanged,
the staging config was removed, and a new trusted HTTPS request still
returned the exact backend response with 200.

The fixture restored the setting and saved a new good baseline. Turning on
maintenance returned HTTPS 503. Rolling back to that baseline through the
API restored HTTPS 200 and the exact live configuration hash of the target
revision. The application row still had maintenance enabled after runtime
rollback. The fixture then disabled maintenance in the database, verified
that the edge and saved state agreed, checked the original settings, removed
the temporary publication and certificate, and revoked the test session.
The guest powered off.

The rejection was at the validation stage. The run did not inject a
systemd reload failure or interrupt an Apply during promotion.
