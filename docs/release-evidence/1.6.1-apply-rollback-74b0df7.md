## Actual validation rejection

The earlier [336b5e0 appliance check](1.6.1-336b5e0.md) rejected a malformed API
request, which did not exercise HAProxy's own configuration validator. This
follow-up used the installed management API, HAProxy 2.8.30 and systemd services.
No validator, service or database operations were mocked.

After an independent baseline check and a new matched backup (root-private,
0600, retained on the VM), the driver waited for API readiness and authenticated
the test operator with password-confirmation step-up. It established an applied
baseline, then changed only `crowdsec_engine_name` through `PATCH /settings` to
the valid identifier `acceptance_missing_engine`, absent from the actual SPOE
file. The saved setting was read back before invoking normal `POST /apply`.

Apply returned **422**. The private API journal contained HAProxy's real parser
alerts, including `No SPOE agent found in file`, followed by the engine's
`validation failed` / `haproxy -c` failure. The live config, crt-list, blacklist,
allowlist, blocked-UA and GeoIP maps retained their recorded bytes and modes
(including absence where applicable). The worker PID, master PID and revision
list were unchanged. The staging config was removed. A new independently
validated TLS connection still returned the exact owned HTTPS marker with 200.

The driver restored the original engine setting in `finally`, applied it and
confirmed the complete settings API response matched the original snapshot.
This tests failure before promotion/reload, not failure of systemctl during
promotion or a crash at an arbitrary point in the transaction.

## Actual revision rollback

With valid settings restored, the owned HTTPS marker application was changed
through the API to maintenance mode. Auto-Apply took effect and a new TLS request
returned **503**. The driver rolled back to the preceding good revision using
`POST /revisions/{id}/rollback`. A new TLS request returned the exact marker with
**200**, the live config hash matched that revision, and a rollback revision was
recorded.

Revision rollback restores generated edge artifacts; it does not rewind the
application rows in PostgreSQL. The maintenance field remained true in the API
after this runtime rollback, as expected. The driver then saved the original
application and applied it to align database and edge again. Subsequent Apply
or startup reconciliation would otherwise render the still-saved maintenance
setting. This check does not claim persistent database rollback.

## Test corrections and recovery

Two initial driver attempts finished unsuccessfully and were retained in the
private logs. The first over-specified the HAProxy diagnostic by expecting the
missing engine name; HAProxy reports the missing SPOE agent without that name.
Its `finally` restored the setting and the independent baseline passed.

The second passed rejection and runtime rollback but its strict final object
comparison detected the legitimate `updated_at` change from saving the test
application. Selected field comparison confirmed that timestamp was the only
difference. A matched-checkpoint restore returned the exact original baseline
before retry. The final driver explicitly checked semantic equality after API
cleanup, then restored the retained checkpoint to return exact timestamps too.
No baseline expectations were weakened or rewritten.

The final owned systemd unit finished with **Result=success, ExecMainStatus=0**.
The actual installed restore reported console Apply success. Independent checks
then matched every baseline application/certificate object and PEM/env/management
certificate hash, verified test TLS/marker, authenticated and Unix stats, core
services and secret access permissions. The original source checkout and backend
were unchanged. Matched restore also removed the temporary test revision history;
selected observations and private driver logs retained the test results.

Authenticated smoke passed **19**, failed **0**, skipped **2** (legacy admin token
and optional MMDB upload). Windows Python 3.14.10 independently verified the test
CA, hostname, exact leaf and HTTPS marker after cleanup. Only the two resolved
failed statuses of the owned test units were reset; journals were retained and
no failed units remained. Full logs, credentials, settings snapshots and backup
stayed on the VM. No private key, env or database dump was exported.
