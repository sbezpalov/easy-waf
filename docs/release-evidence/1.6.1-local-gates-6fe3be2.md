[rollback status failure reproduced on 707f279](1.6.1-local-gates-707f279.md#arm64-offline-installation-and-firewall-status-failure).

contention returns HTTP 503 with `Retry-After`, and the panel retries without

## amd64 offline appliance installation

A clean Ubuntu 24.04.5 VMware guest without a network adapter installed the
verified amd64 ISO under `umask 077` with the CrowdSec snapshot. After reboot,
ten services were active, schema 029 and trusted management HTTPS were ready,
and the installed and live binaries matched the DEB. About reported the exact
commit and its UTC timestamp. An earlier run stopped because the fixture still
expected the previous commit's timestamp. The clean rerun used the timestamp
from Git for `6fe3be2`.

The installed API waited for a brief lock, returned HTTP 503 with `Retry-After`
when the lock stayed held and returned a settled status after release.
Firewall confirmation and automatic rollback passed, preserving the management
guard, managed tables and HTTPS readiness. The time zone API, journal offset,
both optional Zabbix service names and package versions also passed.

Repeat installation without the mounted snapshot preserved CrowdSec and system
APT files. The installed firewall repair kept the active service and unrelated
table. Backup and restore recovered the fixture database, state and configuration
with their expected ownership and permissions. The guest powered off.

## Installed Apply, rollback and WebSocket

Two fresh, disconnected Ubuntu 24.04.5 amd64 VMware guests installed the
verified ISO. Each test authenticated against the candidate management API
and used a synthetic loopback backend with a trusted local certificate.

The HAProxy validator refused a configuration referencing a missing SPOE
engine. Apply returned 422 and preserved the live files, HAProxy processes,
revisions and trusted HTTPS 200. Maintenance returned 503, and revision
rollback restored 200 and the exact target configuration hash. The fixture
realigned the saved application, removed its test data and powered off.

A separate WebSocket received HTTP 101 and echoed a frame over validated TLS.
Apply started a new HAProxy worker while the original one held the connection.
A fresh HTTPS request and stats worked, and the same WebSocket echoed another
frame after 62 seconds of idle time before closing normally. The fixture
removed its test records, revoked the session and powered off.

## PostgreSQL recovery and published HTTPS across reboot

A third fresh, disconnected Ubuntu 24.04.5 amd64 VMware guest installed
the verified ISO and served a synthetic loopback publication over trusted
HTTPS. With PostgreSQL stopped, management readiness returned 503 while
the publication still returned 200 and the expected body. The API and ACME
services each retried at least twice and recovered automatically when the
database returned.

After reboot, the boot ID changed and the services were ready. The same
application returned the exact HTTPS response and certificate leaf. The
fixture removed its test publication and certificate, revoked its session
and reported success before shutdown.
