# Automatic VMware boot recovery — 9cfc841

Date: 2026-11-17. This verifies the dependency binaries from
[9cfc841](1.6.1-crypto-9cfc841.md) on the independent Ubuntu 24.04.5 amd64
VMware copy after its [matched restore](1.6.1-restore-9cfc841.md).
It is scoped unsigned development evidence, not release approval.

## Preflight and actual reboot

Before reboot, all ten checked units were enabled and active: API, ACME, hostd,
HAProxy, PostgreSQL, CrowdSec, `crowdsec-spoa-bouncer`, Fail2Ban, nftables and the
persistent owned marker backend. The failed-unit list was empty. The correct
installed SPOA unit name was resolved during preflight; no service changes were
needed. The previous package and new matched pre-upgrade/current-candidate
archives from the restore exercise remained available, root-private on the VM.

The strict retained application/certificate baseline, trusted marker HTTPS,
secret permissions, four installed payload hashes and three running daemon
executable hashes passed. Full settings/application/certificate objects and
selected configuration/certificate file hashes were captured privately before
reboot.

One delayed systemd reboot request was issued. Boot ID changed from
`8852b045-d1ba-4c2b-ad59-a86edd292f57` to
`b44dadc2-cd79-4ea4-a453-75c698deebcd`.
The first observation encountered a connection reset during reboot. The same VM
was observed again after waiting; the reboot command was not replayed.

## Post-boot evidence

No manual service start, package reinstall or configuration apply was issued
after reboot. The probe completed with exit zero:

- All ten units were enabled and active automatically; the system reported
  `running` and listed no failed units.
- API and ACME ran as `easy-waf`, hostd as root, HAProxy as `haproxy`, and the
  marker backend as `easy-waf`. Their activation timestamps were within the
  first twelve seconds of this boot.
- All four installed payload hashes and API/ACME/hostd `/proc/PID/exe` hashes
  matched the already inspected 9cfc841 DEB.
- Full settings, application and certificate objects matched the pre-boot
  snapshot exactly. Environment, management certificate and test bundle hashes
  matched. The older strict fixture baseline also passed, including timestamps.
- Trusted HTTPS returned the exact marker with the expected leaf certificate.
  A separate Windows Python 3.14.10 client independently verified SNI, its pinned
  test CA, exact leaf and body after reboot.
- Authenticated HAProxy statistics were less than thirty seconds old, without
  a collector error, with `fe_https` OPEN and a backend UP. The independent Unix
  statistics socket check passed.
- The strict API-to-hostd upgrade-status RPC returned explicit `active=false`;
  it did not launch an APT operation.
- Environment permissions stayed root:root `0600`; HAProxy could read its test
  bundle and could not read the environment or management private key.
- nftables listed `inet filter`, `inet easy_waf` and `inet easy_waf_guard` after
  boot. This is table-presence evidence, not a full external firewall test.

## Artifacts, recovery and limits

Ignored local driver and plan: `.ai/artifacts/restore-9cfc841/reboot-probe.py`
and `REBOOT-PLAN.md`. Full before/after snapshots and probe results remain under
the clone's root-private `acceptance-work/reboot-9cfc841` directory, mode `0700`,
with snapshot files mode `0600`. Secrets and backups were not exported.

Recovery would use this clone's VMware console and retained matched package/
backup pair; no recovery intervention was needed. The original source VM stayed
off. PVE, its public certificate and the user's browser session were untouched.
This does not claim a fresh PVE reboot, public ACME renewal, ARM/macOS execution
or external-client blocking test for these binaries.
