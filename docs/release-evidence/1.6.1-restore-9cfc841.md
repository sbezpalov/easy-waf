## Recovery exercise

1. After upgrade, the strict baseline, authenticated HAProxy statistics, Unix
   statistics socket, core services and private-file permissions passed.
2. A new matched current-candidate backup was created. Both new archives were
   owned by root with mode `0600` and remained on the VM.
3. Using the fixture account through the authenticated API and password
   confirmation, maintenance was enabled only for the owned HTTPS application.
   The persisted application field was checked and trusted HTTPS returned 503.
4. The installed `/usr/sbin/easy-waf-restore` restored the current-candidate
   archive, exited zero and reported `apply OK`.
5. The original application and certificate objects matched exactly, including
   timestamps. The certificate bundle, environment and management certificate
   hashes matched the retained baseline. Trusted HTTPS returned the exact
   original marker with status 200 and the expected leaf certificate.
6. Environment permissions were root:root `0600`. HAProxy could read its test
   bundle and could not read the environment or management private key.

An independent Windows Python 3.14.10 client also verified SNI, the explicit
test CA, exact leaf and marker over the VMware address. This exercises test-CA
trust, not public ACME trust.

The current repository smoke script and its environment-parser dependency were
delivered separately and run using the clone's dedicated account: **18 passed,
0 failed, 3 skipped**. Skips were the absent separate admin token, absent MMDB
upload input and GeoIP lookup returning 502. The cause of that lookup response
was not established; no passing GeoIP integration is claimed. Strict baseline,
HTTPS, permissions and core-service checks passed again after smoke; no failed
systemd units were listed.

The owned restore driver ended with `Result=success`, `ExecMainStatus=0`.
Its journal also recorded two missing transient-unit-file messages following
restore; these did not change the terminal success or independent checks.
