good signature by key `D2EB44626FDDC30B513D5BB71A5D6C4C7DB87C81`.
No second runtime or system-wide tool installation was needed on Windows.

Baseline checks recorded Ubuntu 24.04.5 LTS amd64, completed cloud-init, and

## Enrollment and runtime checks

The API initially required enrollment. A dedicated random-password test operator
was created through the normal API with the one-time enrollment secret. The
secret file was consumed/deleted, replay returned HTTP 409, enrollment status
became false and normal login succeeded. Passwords, tokens and full logs remain
private inside the VM. The env and temporary operator file were root-owned 0600.

Only after completing the product install, an owned boot-persistent systemd
backend was added as user easy-waf, bound to loopback and serving a fixed marker.
The normal API created an HTTP-only `.invalid` test publication. Two explicit
Apply cycles each returned the expected HTTP 200 marker and healthy authenticated
stats; independent Unix-socket `show info` also passed. Management requests
verified the generated management certificate with its CA file; TLS verification
was not disabled. API, ACME, hostd, HAProxy, PostgreSQL, nftables, Fail2Ban,
CrowdSec, SPOA bouncer and the test backend were active and enabled.

The candidate's actual smoke script then passed **19**, failed **0**, skipped
**2**, with exit record 0. This run used the dedicated test operator, exercising
authenticated reads/stats and logout. Only the absent legacy admin token and
optional MMDB upload were skipped. No existing PVE/browser session was affected.

`7d6aa766-691a-480f-9a8a-b990d2fada2a` to
`9daab8bd-bf80-41fc-aaa7-3799b0a0c2c8`.
All listed services recovered as active/enabled without manual repair; the
application persisted, and binary/package/schema checks passed again. Two more
explicit Apply cycles preserved the marker and both stats checks. Authenticated
smoke again passed 19/0/2 with exit record 0.

A separate Windows-host HTTP request through the guest's VMware NAT interface
returned status 200 and the exact marker with the test hostname in Host.
PowerShell initially exposed the content as bytes because the fixture omitted
Content-Type; decoding the body corrected the client assertion. This is an
independent local client check, not external WAN acceptance.
