## Source checkpoint and independent copy

The source was the dedicated [pristine-install Ubuntu 24.04.5 appliance](1.6.1-pristine-vmware-b5fa4a4.md),
not the user's PVE appliance. The operator had authorized disposable dev VMs and
configuration reset. A new owned HTTPS `.invalid` publication used the existing
unprivileged loopback marker backend and a freshly generated EC certificate with
the test hostname in SAN. Its certificate mode was manual; no ACME request or
public DNS/WAN change was made. TLS was verified using the test certificate as
an explicit trust anchor, with hostname and served-leaf checks, never insecure mode.

Persisted application/certificate API objects, certificate bundle hash, full env
hash and management certificate hash were recorded privately inside the source.
The packaged `easy-waf-backup` completed with exit record 0 and produced a retained
0600 archive containing the dump, manifest and test PEM. Its digest was recorded
and later checked inside the clone. The installed backup script matched source
byte-for-byte. The initial test PEM directory was inadvertently narrowed to 0700
by the fixture's umask; explicit 0750 corrected its first failed auto-Apply.
The checkpoint and backup were made only after verified HTTPS/stats passed.

The source VM was then shut down gracefully. VMware made a full clone of its
current powered-off state, with an independent VMDK: `parentCID=ffffffff` and
no parent-file hint. The source stayed off and unchanged while the clone ran.
Both are project-owned dev guests; other local VMs and PVE were not changed.

VMware did not copy the relative seed ISO. A clone-specific NoCloud seed supplied
its hostname, key-only operator, network configuration and new SSH host key.
The clone initially reused the source DHCP lease, while Windows retained the old
MAC neighbor entry. Targeted cache removal was denied by OS privileges; it did
not change the entry. A separate static address outside the observed VMware
DHCP pool resolved access. Only the clone's seed/network changed; host routes,
firewall, NAT service and user SSH trust files were untouched. Its new host key
was pinned from the trusted local serial console in a task-local known_hosts.
Before E2E, the clone independently matched all recorded data/hashes and served
the verified HTTPS marker.

## Actual destructive workflow

The unmodified b5fa4a4 `scripts/test-backup-restore.sh` ran with
`RUN_BACKUP_RESTORE_E2E=1` and the clone's private test operator credentials.
A hostname guard refused execution on the source VM. The wrapper supplied a
missing test-PEM input so the script's documented fallback generated its own
throwaway certificate. Credentials were passed only through the VM process
environment, not command arguments or the chat. Full logs and backups stayed
private in guest storage.

The script created its reserved certificate/application, applied, backed up,
stopped the writers, ran the actual admin factory reset, and directly queried
PostgreSQL to assert removal of its application. It then ran the actual source
`restore.sh`, including transactional pg_restore, state/config replacement,
console Apply and service start. Restored API data/config checks passed, followed
by removal of the reserved rows/PEM and re-application of the original edge.
This E2E's temporary archive was removed by its normal successful cleanup; the
separate source checkpoint archive remains retained privately.

The E2E task completed with `MainPID=0`, `Result=success`, `ExecMainStatus=0`
and a separate exit record of 0. Its success marker, reset-query, restored-app,
cleanup and console-Apply checks were all present. Restore in this candidate
was run from the exact source archive: **the DEB currently ships backup, but
does not ship restore.sh or an easy-waf-restore command**. This run does not
claim a self-contained package-only recovery workflow.

## Independent post-restore checks

After the E2E had removed its own test rows, the complete original application
and certificate API objects matched the checkpoint. PEM, env and management
certificate hashes were unchanged. Normal operator login and management TLS
verification worked. HTTPS returned HTTP 200 and the exact marker; the served
leaf matched the recorded test certificate, with normal hostname verification.
Authenticated HAProxy stats and independent Unix-socket `show info` passed.
API, ACME, hostd, HAProxy, PostgreSQL and the original backend were active.

The actual authenticated smoke script passed **19**, failed **0**, skipped **2**,
with exit record 0. It covered operator reads/stats and logout; only the absent
legacy token and optional MMDB upload were skipped. An independent Windows-host
HTTPS request also checked the exact leaf and marker. Only the public test
certificate was copied to that client as a trust anchor; no private key, env,
backup or dump was exported.

The restored clone was then rebooted once. Its boot ID changed from
`614974d6-c91c-4cdf-baf2-79f64eccedaa` to
`e52d0f6a-e260-41ba-a9d7-9b95494e8460`. The same independent data/hash/TLS/stats
checks passed again; authenticated smoke again passed 19/0/2 with exit record 0.
Windows HTTPS passed after reboot too. A shell-wrapper quoting error initially
prevented the boot-ID comparison from reading its root-private file; a root
Python comparison confirmed the changed IDs without another reboot or restore.

Post-reboot access checks confirmed root:root 0600 on easy-waf.env. The actual
haproxy user could not read that env or the management private key, while it
could read the edge certificate bundle it must load. Restore did not require
loosening secret permissions or manually repairing product services.

## Retention, rollback and limits

The original appliance VM remains off with its matched backup and prior pristine
snapshot; the independent restored clone remains running for further testing.
Full disks, private logs, credentials and archives are ignored artifacts. They
are not committed or transmitted in this report. The source VM provides the
retained baseline if the disposable clone is discarded; hypervisor snapshot
restoration itself was not tested here.

This establishes scoped AC-10 recovery on a separate Ubuntu amd64 appliance copy
with the same product/package/database version. It does not prove cross-version
restore, public ACME/WAN, DNS-01, optional MMDB, HA clients, arm64 or macOS.
No new product code, release tag, branch or push was made. Final signed-release
and remote CI/E2E gates retain their existing limits.
