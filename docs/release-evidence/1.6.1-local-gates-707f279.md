## amd64 offline appliance installation

A fresh Ubuntu 24.04.5 amd64 VMware guest with no network adapter installed
the exact ISO under `umask 077` with the verified CrowdSec snapshot. It
rejected the missing snapshot before provisioning. After reboot, ten units
were active, the database was on schema 029, management HTTPS was trusted,
CrowdSec LAPI responded, HAProxy validated and the installed and running
binaries matched the DEB. Authenticated About reported the expected source
revision and commit date.

The installed API passed time zone, audit and journal checks. It confirmed
one nftables change and allowed another to roll back, with the managed
table, guard and HTTPS readiness verified. The service controls exercised
both Zabbix package names with synthetic systemd units. About reported each
installed package version and removed the row after package removal.

Repeat installation without the mounted snapshot preserved CrowdSec and
the system APT sources and indexes. The shipped firewall repair toggled
the Zabbix port rule while keeping the active service, guard and unrelated
table. Installed backup and restore recovered synthetic database, state and
configuration data and returned the appliance to trusted readiness. The
guest powered off successfully.

## ARM64 offline installation and firewall status failure

A disconnected Ubuntu 24.04.5 arm64 guest in QEMU 8.2.2 installed the exact
ISO from a read-only device under `umask 077` with its clock behind the bundle's
APT metadata. It refused a missing CrowdSec snapshot, then completed the
full-profile installation with the verified snapshot. The baseline system APT
sources and indexes were preserved. After reboot, ten units were active,
the database was at schema 029, management HTTPS was trusted, CrowdSec LAPI
answered and HAProxy validated. The installed binaries and three running
daemons matched the package. The installed time zone check passed.

Firewall confirmation succeeded. The second change reverted after its timer
expired, as the hostd journal confirmed. A concurrent pending-status read
returned HTTP 500 because the rollback process still held the lock. The
fixture exited 1, so the later ARM64 assertions and repeat installation
remain open for the corrected build.

## Installed Apply rejection and rollback

A fresh Ubuntu 24.04.5 amd64 VMware guest installed the verified `707f279`
ISO without a network adapter. Authenticated About confirmed the candidate
revision. A temporary loopback publication served HTTPS with a verified
local trust anchor. The password-confirmed API Apply with a missing SPOE
engine returned 422. The actual `haproxy -c` rejection preserved the live
files, master and worker, revision list and trusted HTTPS 200 response.

Maintenance returned HTTPS 503. API rollback restored HTTPS 200 and the
target revision's exact HAProxy configuration hash. The fixture realigned
the saved application with the live edge, restored settings, removed its
publication and certificate, revoked its session and powered off. The
rejection exercise covered validation before promotion.

## Installed WebSocket continuity across Apply

A separate fresh Ubuntu 24.04.5 amd64 VMware guest installed the same ISO
without a network adapter. It published a loopback echo server using the Home
Assistant profile and a locally trusted certificate. The client checked the
leaf certificate, received HTTP 101 and verified the first echo.

An authenticated Apply created a new HAProxy worker while the original worker
kept the WebSocket open. Fresh HTTPS requests and HAProxy stats succeeded.
The same WebSocket echoed another frame after 62 seconds idle, beyond the
ordinary 50-second HTTP timeout, and closed normally. The fixture removed its
publication and certificate metadata, revoked its session and powered off.
This exercise used a synthetic backend on the isolated VM.

## PostgreSQL recovery and surviving HTTPS across reboot

A separate fresh Ubuntu 24.04.5 amd64 VMware guest installed the exact ISO
without a network adapter. A temporary loopback publication served trusted
HTTPS. When PostgreSQL stopped, management readiness returned 503 and a
new request to the published route still returned 200 and the expected body.
API and ACME each retried at least twice while PostgreSQL was down. Both
recovered automatically when PostgreSQL returned.

After a real reboot, the boot ID had changed and the management API was
ready on the candidate revision. The application was still present and HTTPS
returned the same trusted certificate leaf and body. The fixture removed
its test records, revoked the session and powered off.
