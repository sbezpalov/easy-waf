## Real HAProxy WebSocket coverage

The previous Home Assistant live test requested `/api/websocket` as an ordinary
GET and accepted HTTP 200. It proved route policy but could not detect a broken
Upgrade or tunnel. The shared controlled backend now recognizes a real WebSocket
request and performs HTTP 101 Upgrade. Fixed handshake and masked Hello vectors
from [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455) avoid adding a dependency
or implementing a general WebSocket stack in the fixture.

The client validates Upgrade/Connection/Accept headers, waits 1.5 seconds,
sends the exact valid masked frame and verifies the unmasked echo. Only the
private generated test config's HTTP client/server timeouts are shortened to
one second; its tunnel timeout remains unchanged. The exchange therefore proves
continued bidirectional tunnel traffic beyond the test HTTP idle limits.
The `ha-mcp` publication rejects the same Upgrade request to `/api/websocket`
with HTTP 404, preserving the MCP-only allowlist. Existing normal-route and
probe-blocking assertions remain in the test.

A separate negative-control snapshot removed the backend's upgrade handler.
The new protocol assertion failed with
`WebSocket home-assistant.example.test: HTTP 200, want 101`. That private source
was restored before the positive run; no production behavior was altered to
make the checks pass.

## Read-only probe of the user's Home Assistant backend

From the dedicated VMware clone, a direct request to the user-specified backend
returned HTTP 200. A real direct WebSocket handshake returned 101 with the valid
Accept value and an initial `auth_required` message. The probe sent a normal
masked close frame without submitting credentials or requesting entities/actions.
That initial message matches the [documented HA protocol](https://contributors.home-assistant.io/core/internals/websocket-api/).

The paired direct HTTP request with `X-Forwarded-For` returned 400. The separate
Windows native direct-HTTP probe timed out after eight seconds; that observation
was not treated as backend absence because the clone reached it successfully.

HA's [reverse-proxy documentation](https://www.home-assistant.io/integrations/http/#reverse-proxies)
requires forwarded-client trust and the address of the immediate proxy as seen
by HA. The 200/400 difference is consistent with missing trust for the new NAT
test path; confirming the precise cause requires HA logs/configuration. Those
were not read or changed. A NAT guest may appear with its host's source address.
The guide now explains this diagnostic and distinguishes a normal GET from a
real WebSocket channel.

This probe covered a direct backend request with proxy headers. No new WAF
publication targeting the actual HA service was created, and PVE/public-domain
configuration was unchanged. Authenticated HA, Companion/mobile, entity actions,
MCP tools and public-WAN WebSocket acceptance remain open. Controlled HAProxy
transport success does not establish those client workflows.
