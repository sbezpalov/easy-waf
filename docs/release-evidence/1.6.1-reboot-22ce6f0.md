# Actual PVE reboot recovery — 22ce6f0

Date: 2026-11-17. Dedicated, operator-authorized Ubuntu 24.04.4 amd64 PVE dev VM.
Installed [22ce6f0 candidate](1.6.1-acme-contact-22ce6f0.md); product source,
package, application, certificate and global settings were unchanged in this
follow-up. Two actual reboots occurred, separated by an owned test-fixture repair.

## Preflight and first attempt

The current payload, full app/cert/settings snapshots, renewed served public
certificate, trusted HTTPS response and existing root-private matched checkpoint
were verified before reboot. Product services were enabled.

The controlled 127.0.0.1:37993 backend was running in a transient systemd unit,
which would disappear on reboot. A separate persistent acceptance-only backend
was therefore enabled without starting it while the old transient listener was
still active. Its address and exact 24-byte response were identical. No product
publication or unit was changed.

First actual boot-ID transition:
`4ad277e4-f2d9-46e4-adc8-e2038752cebe` →
`615842e2-a02d-479b-8df6-f1724868fbee`.
All nine checked product services were active afterwards, but the new test backend
failed to start. This first attempt is **not** recorded as complete HTTPS recovery.

The acceptance script had been placed below an existing root-private 0700 parent,
so User=easy-waf could not read it. The first observer terminated without a success result before fixture recovery;
a later manual start was not labeled as automatic boot recovery.
The fixture moved to its own directory containing only its public marker script;
the original private directory's permissions were unchanged. The first repair
also exposed root umask 077 masking mkdir's requested mode, so the new owned
public-only directory received an explicit 0755 mode. The service user's actual
read/compile access was checked before proceeding.

The fixture was manually recovered and the edge returned its exact trusted 200
response after HAProxy health checks converged. An immediate probe during that
warm-up had observed a mismatch; the subsequent existing-state read passed,
without another service restart. These fixture preparation errors are not
attributed to the appliance code or silently counted as a pass.

## Second actual reboot and independent checks

After the specific fixture correction, preflight again matched the original
product state, verified fixture enablement and service-user access, and recorded
a separate one-request reboot marker. This was a deliberate test after repair,
not a replay caused by an observation timeout.

Second actual boot-ID transition:
`615842e2-a02d-479b-8df6-f1724868fbee` →
`1f1d2c3b-f944-4591-a704-7869301c6c26`.
No manual service start was issued after this second boot.

All post-reboot probes completed with exit 0:

- Nine product services (API, ACME, hostd, HAProxy, PostgreSQL, CrowdSec, SPOA,
  Fail2Ban and nftables) plus the owned backend were active automatically.
  The global failed-unit list was empty at inspection.
- Complete application, certificate and global settings objects matched the
  accepted pre-install snapshots, including the production ACME configuration.
- All four installed binary hashes remained the 22ce6f0 package payload.
- Actual API/ACME processes ran as easy-waf; the HAProxy master ran as haproxy.
- Trusted HTTPS served the same renewed leaf, exactly matching the DB-referenced
  fullchain, and returned the exact controlled backend response.
- Served UI/CSP equality and management-secret permissions passed again:
  root-private environment, service-owned 0600 management key, neither readable
  by HAProxy.
- A separate authenticated stats request returned a fresh collection without
  error, HTTPS frontend OPEN and the owned backend UP. Active unit files alone
  were not used as proof that the Unix stats path worked.
- An independent Windows Python 3.14.10 client passed default trust/public-name
  SNI, the expected leaf fingerprint and HTTP 200 with the exact body hash.

Preserved response SHA-256:
`77918cd2a7bf0c261805463f239174c32f630ce14c6d036beb4d34f1f3002aa3`.
The certificate was obtained in the [cb2d0a7 renewal](1.6.1-http01-renewal-cb2d0a7.md);
no new CA request was made here.

## Retained fixture, recovery and limits

The unprivileged acceptance backend remains enabled while the dev marker
publication is used. Its script is in a dedicated public-only directory, with
NoNewPrivileges, PrivateTmp, ProtectSystem/ProtectHome, empty capabilities and
restricted address families. This is test infrastructure, not a new product unit
or a dependency introduced into appliance packaging. The obsolete transient
listener naturally disappeared on reboot; no user service was removed.

The retained matching package and private checkpoint remain the recovery pair.
Before disabling/removing the owned backend fixture, replace its role or remove
its test publication through the normal API; stopping it alone would leave that
publication without a backend. No product data rollback was needed.

Ignored local evidence: `.ai/artifacts/reboot-22ce6f0/` contains both acknowledged
boot baselines, plans/scripts, the safe successful result and Windows result.
Full app/cert/settings snapshots and the first fixture-failure record stay private
on the VM. No credentials, keys or backups were exported; no operator logout or
password reset was performed.

This supplies actual current-candidate reboot/TLS/stats evidence. Late-PostgreSQL
failure injection, external mobile/WAN access after reboot, DNS-01, restored-copy
recovery and privileged UI workflows were not rerun. The earlier late-DB evidence
retains its [recorded candidate scope](1.6.1-336b5e0.md). macOS and ARM boot were not
tested. No branch, push, tag, signature or release was created or approved.
