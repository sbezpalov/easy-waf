Test date: 2026-11-16, Europe/Moscow. The dedicated Ubuntu VMware clone ran the
inspected [677a499 package](1.6.1-packaged-restore-677a499.md), amd64 DEB SHA-256
`9481c29655d3922d2a5e1e085f986384f49ef86766edcb98f15b9ee5a5c85028`.
One independently verified Windows WSS connection survived 62 seconds of
application silence and an actual management API Apply/reload, then exchanged
another frame and completed normal close.

## One live connection across Apply

The Windows client verified the configured certificate chain against the existing
explicit test CA, checked the hostname and exact served leaf, and established
HTTP/1.1 101 with a valid Sec-WebSocket-Accept. It sent a masked text frame and
checked its unmasked echo, then sent no application data for 62 seconds.

While that socket remained open, the normal management API performed operator
login, password step-up and Apply. Process observation confirmed the same HAProxy
master PID, a newly created worker, and the old worker remaining alive during
the stream. This was an observed reload, not an unchanged/no-op assumption.
Authenticated API stats and independent Unix-socket `show info` passed after
the worker transition. A new independent Windows HTTPS request also received
the exact marker during the existing connection's idle period.

The installed config's ordinary HTTP client timeout was 50 seconds; it was not
shortened for this appliance experiment. After 62.0 seconds of silence, the
client sent another text frame on the same TLS/WebSocket connection and received
the expected echo. It then sent masked close code 1000 and verified the peer's
matching close response. The native client process completed with exit 0.
The silence included the Apply operation and exceeded the normal HTTP timeout.
