# Direct package upgrade and HAProxy recovery — b5fa4a4

Follow-up: [pristine Ubuntu installation and reboot](1.6.1-pristine-vmware-b5fa4a4.md)
subsequently passed on a separate VMware guest. The limits below describe this
PVE package-upgrade experiment.

Test date: 2026-11-16, Europe/Moscow. Candidate source:
`b5fa4a4d680fa62723a6de15033c7594bb9c21bd`. Direct APT migration from the
authenticated published 1.6.0 package passed on the dedicated Ubuntu 24.04.4
amd64 PVE dev appliance, including recovery of its missing HAProxy stats socket.
This closes that scoped package-upgrade check; pristine OS installation remains open.

## Baseline and reproduced failure

The operator authorized resetting this dev configuration. Original state, database,
matched backups and rollback packages remain private on the VM. The baseline reused
provisioned OS/PostgreSQL/CrowdSec dependencies; it was not a pristine installation.
Operator credentials and management TLS/JWT files were retained without resetting
the password. Private backups were not exported.

The starting package was the [signature-verified published 1.6.0](1.6.1-release160-migrations.md).
All four installed binaries matched its DEB; dpkg/API reported 1.6.0 and the
database contained exactly 19 migrations. The unchanged old installer ran from
`/`. An owned HTTPS publication forwarded to an unprivileged loopback backend
serving only a fixed marker. The retained public certificate passed normal CA
and hostname verification, and HTTPS returned HTTP 200 with that marker.

An ordinary Apply on the old installation reproduced removal of the stats socket
pathname while HTTPS continued working. A direct APT upgrade to the earlier
d0eabdf DEB exited successfully and migrated to 27 migrations, preserving app,
certificate and HTTPS, but left stats unavailable with `no such file`. This was
a failed acceptance result, not waived as an old-baseline limitation.

## Repair and regression checks

The packaged postinst now queues a nonblocking HAProxy cold restart during an
upgrade only when it installed the managed drop-in and HAProxy is already active.
The restart precedes queued API/ACME restarts and recreates the old missing socket
with the managed service identity and working directory. Stopped services and
unowned custom drop-ins are preserved. A brief client reconnect is documented;
there is no synchronous owner restart or immediate fallback while APT owns locks.

The scheduling regression failed before the repair with
`missing queued managed HAProxy restart: all`. Afterward, extracted postinst
scheduling and actual temporary-filesystem drop-in cases passed on Windows
(Git Bash 5.3.15) and Ubuntu 24.04. ShellCheck 0.11.0 on Windows, ShellCheck 0.9.0
on Linux, POSIX shell syntax and full `make verify` passed for the tested source.
The real systemd/APT lifecycle fixture passed all seven subcases in 18.53 seconds,
including synchronous-owner negative control, lock waiting, identity denial,
broker survival, stopped-state preservation and self-package removal.
It used a private container cgroup namespace without host PID/network namespaces
or a Docker socket. No runtime Go code changed in this repair.

## Actual fixed APT transition

A checksum-verified private backup of the actual 1.6.0/schema-19 checkpoint was
restored into a separate local database. Original directory modes were restored
after safe archive extraction. Baseline binary/package/schema checks were repeated,
and the ordinary old Apply again reproduced the missing socket with HTTPS intact.

Only APT then installed the checksum-verified candidate amd64 DEB, preserving
conffiles. No source installer or manual HAProxy restart followed APT. The task
completed with `MainPID=0`, `Result=success`, `ExecMainStatus=0` and a separate
exit record of 0. Independent process checks confirmed a changed master PID,
HAProxy UID and `/` working directory. Subsequent reloads preserved that new PID.

Both dpkg and API reported 1.6.1; all four installed binaries matched the candidate
DEB and the database contained exactly 27 migrations. The persisted application
fields, complete certificate row, PEM file hashes and env bytes were unchanged.
The served leaf matched the retained PEM; default-CA-verified HTTPS still returned
the expected marker. Two API Apply cycles each passed authenticated stats and
an independent Unix-socket `show info` check.

The exact candidate smoke script completed with task and exit record 0:
12 passed, zero failed, five skipped (legacy token, authenticated reads, stats,
optional MMDB upload, logout). Separate operator checks covered reads and stats.
MMDB upload and logout were not performed; the smoke run did not revoke browser
sessions through an authenticated logout.

Native Edge displayed v1.6.1. After signing in, the operator manually completed
password confirmation for Config → Apply HAProxy. The panel displayed
`HAProxy config applied` and revision time `2026-11-16T17:33:47.500418Z`.
Read-only verification then required the latest revision label `ui` and rechecked
unchanged app/certificate/env, trusted HTTPS and working stats. The browser console
contained an earlier login HTTP 401, so this run does not claim a clean console.

## Limits and rollback

The current publication serves the owned test marker, not the original HA backend.
Its transient backend is retained for continued testing and does not establish
boot persistence. No reboot, fresh public ACME issuance or external-client retest
was performed on b5fa4a4. Earlier [script-upgrade and whole-project race/security
checks](1.6.1-script-upgrade-d0eabdf.md) retain their original candidate scope;
the whole Go race suite and vulnerability scan were not repeated for this shell-only
repair. Pristine Ubuntu install, final-candidate remote CI/E2E/signatures, arm64
boot and macOS development checks remain open. No release tag or push occurred.

Rollback uses the operator's snapshot or a matched private state/database backup
with the corresponding retained package and env selection. A binary downgrade
alone must not be used against the migrated database. The pre-test original
database, previous failed-upgrade database and matched old checkpoint are retained.
