## Local candidate gates

The complete Linux run used Ubuntu 24.04, Go 1.27.4, PostgreSQL 16 in a disposable
container, HAProxy 2.8.30, Node 18.19.1 and golangci-lint 2.15. Vet, whole-project
lint, golden rendering, serial `go test -race -count=1 -p 1` across all packages
(golden rendering excluded from duplication) and full `make verify` passed.
The PostgreSQL fixture had no external network or host ports and was removed.

The separate tagged HAProxy command exposed relative fixture paths incompatible
with the validator's `/` working directory. Windows source archiving also emitted
CRLF for the previously unattributed OVF script. These gates initially failed;
they were not waived. At dc1eae4, private golden config/crt-list materialization
uses absolute cert/SPOE/map paths, OVF scripts have LF attributes and join the
line-ending guard. Real golden validation and HA route checks, tagged vet/lint,
full verify, all scripts/OVF syntax and ShellCheck then passed on that exact staged
archive. Expanded tagged lint also found and resolved preallocation in the HA
live test. No golden expectations or runtime validator behavior were weakened.
Whole-project race was run on d0eabdf, not repeated for this verification-only fix.

Pinned govulncheck 1.9.0 with the official database reported zero called-code and
zero imported-package vulnerabilities. One module warning remains:
[GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932) affects unimported OpenPGP
packages in x/crypto. No suppression was added; this is not a claim of zero
module advisories or a comprehensive security audit.

## Actual starting appliance

The operator explicitly permitted resetting this dedicated PVE dev configuration.
A matched backup completed and was validated privately on the VM. Its original
database was not dropped; original state/env and a rollback package/script remain
private there. A new local database and fresh runtime state were used for 1.6.0.
The operator credential and management TLS/JWT files were retained without a
password reset. Already-provisioned OS/CrowdSec/PostgreSQL packages were reused;
this is not a pristine Ubuntu installation.

The starting DEB was the [authenticated published 1.6.0](1.6.1-release160-migrations.md).
All four installed binaries matched that DEB byte-for-byte, dpkg and API reported
1.6.0, the ledger had exactly 19 migrations, operator login worked and services
were active. Invoking the unchanged old installer from a private source directory
initially caused its root fallback/stats permission problem; rerunning it from
`/` and restarting restored the unprivileged HAProxy unit and healthy stats.

A loopback backend running as easy-waf served only a fixed marker. The old API
created an HTTPS publication using the retained valid public certificate. A
default-CA-verified request for the public hostname returned HTTP 200 and that
marker before upgrade. The fixture helper's umask initially prevented HAProxy
from traversing a copied cert directory; restoring the original directory modes
fixed the fixture. Product source and signed baseline binaries were unchanged.

## Script transition and verification

The actual target `scripts/upgrade.sh` ran against the checksum-verified target
tarball and completed with exit 0. Readiness checks found all four installed
binaries matching the target artifact, API 1.6.1 and exactly 27 migrations.
Existing application fields, certificate row, PEM file hashes and complete env
bytes were preserved. Application timestamps were compared at PostgreSQL's
microsecond precision: the old POST response had retained additional Go
nanoseconds, while the persisted GET truncated them (observed difference 524 ns).

Trusted HTTPS still returned the marker; the served leaf matched the unchanged
configured PEM. Two API Apply operations passed, with both authenticated stats
and an independent Unix-socket `show info` check after each. The normal smoke
script passed 12 checks, failed zero and skipped five: absent legacy token,
authenticated reads, authenticated stats, optional MMDB upload and logout.
Separate operator API checks covered reads/stats; logout and MMDB upload were
not exercised. An initial command-wrapper quoting error gave the wrapper exit 2
despite a successful smoke summary; a file-based wrapper was corrected and the
repeat task and smoke exit record both reported 0.

Native Edge remained authenticated and showed target version 1.6.1. Config →
Apply requested step-up; the operator entered the password. The UI displayed
`HAProxy config applied`, a new current revision and zero console messages.
Read-only verification matched the latest revision label `ui` and confirmed
HTTPS, cert files, app fields and stats after that UI action.

## Package-method limit and current state

The script path intentionally does not manage dpkg, which still reported 1.6.0
after its binaries became 1.6.1. The acceptance instructions had incorrectly
recommended that unpackaged path to all installations, without even its required
input argument. They now distinguish APT package upgrades from script upgrades.

After this experiment, APT installed the verified candidate DEB. Only source
shadow units byte-identical to the packaged units were moved to private retained
storage. Its task and exit record reported 0. Both dpkg and API now report 1.6.1;
preserved data, trusted HTTPS and healthy stats were checked again. This alignment
does not prove the package's own migration from schema 019: that still requires
a separate actual 1.6.0 checkpoint and direct APT transition.

The active dev publication is the owned test marker, not the original HA backend;
its backend service is intentionally retained for the next acceptance stage.
Original configuration remains privately retained. Pristine install, direct
package migration, final-candidate remote CI/E2E/signatures, arm64 boot and macOS
remain open. No snapshot restoration, backup export, release tag or push occurred.
Rollback can restore original state/env and DB selection with the retained prior
package, or use the operator's snapshot and matched private backup.
