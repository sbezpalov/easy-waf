## Actual binaries and isolated PostgreSQL

A disposable PostgreSQL 16 container had no external network or published host
ports. A separate read-only Ubuntu 24.04 test container shared only its network
namespace, with private tmpfs execution/state directories and dropped
capabilities. Before extraction, each selected tarball was rechecked against
its pinned digest.

1. The actual published 1.6.0 `easy-waf-api -sync-settings-only` initialized the
   empty database successfully. SQL assertions found exactly 19 migration
   records, ending at 019. Go build metadata identified compiler 1.27.3.
2. SQL inserted synthetic applications, a certificate and a user, then saved
   their full row JSON and all old migration records inside the fixture DB.
   One app used an existing certificate, WebSocket and explicitly required
   backend TLS verification; another represented a legacy orphan certificate
   reference. The user hash marker could not authenticate and was not a real
   credential. No operator data was copied from the dev appliance.
3. Candidate `93eab9f2f3ee0696c26b3b81f861d683e2ffa523` used the actual amd64
   tarball documented in [its package report](1.6.1-confirmation-dialog.md),
   SHA-256 `dde1a4c7f75eda8e5fc0fe981d02b617161e016e27cea141c68e308340f4be4d`.
   Its `easy-waf-api -sync-settings-only` completed successfully with compiler
   1.27.4 and advanced the ledger to exactly 27 records, ending at 027.
4. Assertions compared every pre-existing app/certificate/user field, including
   timestamps and password-hash marker, and all old ledger records. They stayed
   unchanged except the deliberately orphaned certificate reference, cleared
   by migration 026. Existing users acquired admin role with 2FA disabled; new
   application policy, maintenance, backend-pool and forward-auth columns had
   their expected inactive defaults. The ACME intent table existed.
5. A transactional deletion attempt against the linked certificate raised the
   expected foreign-key violation. A second candidate run and the complete
   assertions passed again. Both containers terminated; the fixture database
   was removed in cleanup.

## Remaining appliance gate

This run exercises real embedded migrations through real release binaries. It
does not run the old API service, installer, systemd, HAProxy, public traffic,
certificate files, UI Apply or backup/restore. In particular, the SQL certificate
paths refer to fixture placeholders; no certificate-file preservation claim is
made. No 1.6.0 package was installed or downgraded on the current PVE dev VM,
which already contains the operator's HA publication.

Full acceptance still needs a separate clean Ubuntu 24.04 appliance, a working
1.6.0 deployment with matched state/config backups, actual `scripts/upgrade.sh`,
smoke and UI Apply. VMware Workstation was found on the Windows host, but no VM
was running and registered VMs belonged to other projects; none was started or
changed. The operator's separate-stand preference remains pending.

No current-candidate signature, release tag or push was performed. There was no
dev-appliance state change to roll back; all database mutations were confined
to the disposable fixture. The original VM snapshot and private backups were
not accessed or exported.
