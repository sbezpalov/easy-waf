## Package identity

The Release workflow's preflight and build steps ran locally on Ubuntu with
Go 1.27.4 from the archived source tree. The generated 1.6.1 notes included
the privileged confirmation fix. The workflow and a separate Windows check
agreed on all four SHA-256 hashes.

Both DEBs reported the expected version and architecture. The four shared
executables were byte-identical between the DEB and tarball for each
architecture. All four amd64 commands reported version 1.6.1.

## Installed appliance and browser result

The isolated Ubuntu 24.04.5 amd64 VMware guest reinstalled the verified DEB
through APT with package sources disabled. The four installed executables
and three running easy-waf daemon executables matched the package. The
environment, management certificate, HTTP fixture publication and active
backup timer were preserved. The served panel HTML matched the committed
embedded HTML, with SHA-256
`c628c95b5b79a17d4a5dede58283be98200d377429be2dd7bd02bcf919c134a0`.

Chrome 157.0.8103.79 on Windows signed in with a synthetic account in a
temporary browser profile that trusted the guest's pinned certificate key.
Clicking **Edge changes → Apply HAProxy** opened the password prompt. Clicking
**Cancel** sent no confirmation and left the latest revision unchanged.
Clicking **Apply HAProxy** again and submitting the prompt with a native click
on **Confirm** produced HTTP 200 from both password confirmation and the
retried Apply. The revision API returned a new active revision labelled
`ui`. The browser recorded no JavaScript exceptions or security errors.

An independent Windows HTTP request through HAProxy received the expected
fixture body before the reinstall and after browser Apply. HAProxy and the
management API remained active, and the guest then shut down normally.

This closes browser-driven Apply for the tested amd64 candidate. The arm64
artifacts were inspected. Signed-release verification and acceptance on the
published artifacts are separate gates.
