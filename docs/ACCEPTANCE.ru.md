# Приёмка, которую делают руками

[English](ACCEPTANCE.md) | **Русский**

Реализация и тестовое покрытие перечислены в
[IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md), но не подтверждают приёмку
конкретного релизного кандидата на appliance. Открыты публичный ACME, WAN,
CrowdSec на хосте, чистая установка, обновление и настоящий reboot.
`scripts/acceptance-checklist.sh` только печатает список, а не выполняет приёмку.

Для каждого кандидата скопируйте [шаблон отчёта](RELEASE_ACCEPTANCE_TEMPLATE.md).
Запишите точный тег/версию, коммит и checksum пакета. Результат другого коммита
или минимальной пакетной fixture не подтверждает этот кандидат.

Не отмечайте пункты сделанными по контейнеру, поддельному DNS или staging-каталогу ACME.

## AC-03 — настоящий сертификат

На appliance Ubuntu 24.04, доступном на порту 80 (HTTP-01), или с боевыми
учётными данными DNS в `dns_credentials_env_file` (DNS-01):

1. Выключите глобальный `acme_staging` и `staging` каждого тестового сертификата,
   укажите `acme_email`, на который приходит почта. Любой включённый staging-флаг
   выбирает тестовый CA, не подходящий для проверки доверия браузера.
2. Выпустите один сертификат по HTTP-01 и один по DNS-01 (Cloudflare, CloudNS,
   Route53 или тот webhook-провайдер, которым вы пользуетесь).
3. Убедитесь, что браузер доверяет публичному имени, а `not_after` в
   `GET /api/v1/certificates` совпадает с сертификатом, который отдаёт HAProxy.
4. Запросите продление через `POST /api/v1/certificates/{id}/request-issue` с `{}`
   или дождитесь 30-дневного окна. Используйте операторскую сессию, обычный XHR-
   заголовок и подтверждение пароля (step-up), необходимые для изменений.
   Пустой объект сохраняет режим проверки. При HTTP 409 перечитайте строку и
   повторите запрос. Сравните сертификат, реально отдаваемый на 443, с новыми
   PEM-файлом, на который указывает БД, и записанными сроками после apply:
   изменения файла недостаточно.
5. Один раз сломайте проверку (закройте порт 80 или отзовите DNS-токен) и
   убедитесь, что строка стала `failed`, дашборд показывает внимание, журнал
   `easy-waf-acmed` предупреждает в течение суток и — если задан
   `notify_webhook_url` — приходит один POST, а сам URL в журнал не попадает.

## AC-04 — клиент не из LAN

Из сети, которая не является LAN appliance, откройте опубликованное имя. Для
этого нужен проброс 443 (и 80 для HTTP-01) на этот хост, DNS на него и
сертификат из AC-03. Запишите IP клиента в журнале HAProxy и IP, который видит
бэкенд (`X-Forwarded-For`).

## AC-05 — CrowdSec на appliance

Ночной контейнерный тест (`scripts/test-crowdsec-e2e.sh`,
`.github/workflows/e2e.yml`) уже показывает, что сгенерированный конфиг отвечает
403, когда настоящий баунсер так решил, и пропускает трафик, когда баунсер
недоступен. На самом appliance:

1. `crowdsec-firewall-bouncer` для этой проверки не нужен: проверяется SPOE-баунсер HAProxy.
2. Добавьте решение для тестового клиента (`cscli decisions add`).
3. Запросите опубликованное имя с этого клиента и запишите 403.
4. Удалите решение и запишите, что следующий запрос проходит.
5. Остановите баунсер, запишите, что трафик всё ещё проходит, и запустите его снова.

## Установка и обновление

- Чистая Ubuntu 24.04: `sudo bash scripts/install.sh`, затем
  `sudo bash scripts/smoke-appliance.sh`.
- Обновление appliance, на котором действительно работает 1.6.0: до начала
  запишите версию API, хеши установленных бинарников и версию dpkg для пакетной
  установки. Проверьте подлинность кандидата и сохраните согласованный backup.
  Для пакетной установки используйте APT с проверенным DEB, например
  `sudo apt-get -o Dpkg::Options::=--force-confold install ./easy-waf_1.6.1_amd64.deb`
  для кандидата 1.6.1 на amd64; выберите фактические версию и архитектуру.
  После обновления версии dpkg и API должны соответствовать кандидату.
  Для установки без пакета используйте
  `sudo bash scripts/upgrade.sh /path/to/verified-binaries-or.tar.gz`.
  Этот путь заменяет бинарники, но не обновляет метаданные dpkg.
  Затем выполните тот же smoke-скрипт и один Apply из панели. Проверьте текущий
  набор миграций, сохранность конфигурации и сертификатов, reload HAProxy,
  рабочую статистику и опубликованный сервис. Перезапись tarball с последующим
  выравниванием пакета не доказывает пакетную миграцию исходной схемы 1.6.0.

## AC-08 — настоящая перезагрузка

На отдельном тестовом appliance запишите boot ID, перезагрузите его и после
подключения убедитесь, что boot ID изменился. Запустите smoke-скрипт, проверьте
readiness и опубликованный HTTPS-сервис. Проверьте восстановление API, ACME и
hostd, в том числе при позднем запуске PostgreSQL. Включённых unit-файлов и
перезапуска fixture-сервиса недостаточно для закрытия критерия.

Перед одобрением кандидата из отчёта запишите дату, хост (без секретов) и
результат каждого пункта. Контейнерный или CI-прогон не закрывает пункты
приёмки appliance автоматически.
